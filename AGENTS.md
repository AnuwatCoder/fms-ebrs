# FMS-EBRS Project Instructions

These instructions apply to the entire repository. Follow the user's current request first, then these project rules. Inspect the existing implementation before changing code and keep new work consistent with nearby files.

## Project Overview

FMS-EBRS is an equipment borrowing and return system built with:

- PHP 8.4 and Laravel 13
- Blade, Livewire 4, Bootstrap 5.3, Lucide, and ApexCharts
- Spatie Laravel Permission for roles and permissions
- Authentik/OpenID Connect for authentication
- PostgreSQL in normal environments and in-memory SQLite for tests
- Pest 4 for Feature and Unit tests

User-facing text is primarily Thai. Keep code, class names, database columns, events, permissions, and test descriptions in clear English unless an existing convention requires otherwise.

## Required Architecture

Use the following flow for application features:

`Route -> Controller -> FormRequest -> Action/Service -> Model -> Blade/Resource`

- Keep controllers thin. Controllers may coordinate dependencies and choose a response, but must not contain substantial business rules or query construction.
- Put validation and request authorization in a dedicated `FormRequest`.
- Put state-changing business logic in a focused class under `app/Actions`.
- Put reusable read/query logic under `app/Services`.
- Use Eloquent models and relationships instead of manual joins when this remains efficient and clear.
- Use API Resources for JSON endpoints. Existing HTML endpoints return Blade views.
- Do not introduce a Repository layer unless multiple persistence implementations or repeated complex persistence logic justify it.

## Laravel and PHP Conventions

- Follow Laravel conventions, PSR-12, SOLID principles, and the style of adjacent files.
- Declare parameter and return types. Add useful array-shape PHPDoc when PHP cannot express the type.
- Prefer constructor injection and Laravel container resolution over service locators or manual construction.
- Use PHP backed Enums for workflow states and actions. Never add new magic status strings when an Enum belongs in the domain.
- Use named routes and route-model binding. Public equipment URLs use `public_id` through the model route key.
- Use configuration files for application settings. Never call `env()` outside `config/*.php`.
- Do not hard-code credentials, tokens, hosts, or environment-specific secrets.
- If a new environment variable is required, document a safe empty/default value in `.env.example` without exposing a real secret.
- Keep comments focused on intent or non-obvious constraints; do not narrate straightforward code.

## Domain and Workflow Rules

- Treat borrowing, approval, checkout, return, maintenance, administration, and audit behavior as domain workflows, not CRUD-only operations.
- Use `DB::transaction()` when a mutation changes multiple records, writes an audit entry, advances a sequence, or performs a workflow transition.
- Lock mutable workflow rows or sequence rows with `lockForUpdate()` when concurrent requests could create inconsistent state.
- Validate allowed transitions with the relevant Enum before changing workflow state.
- Re-check equipment availability inside the transaction; browser state and request validation alone are not sufficient.
- Preserve the automatic code formats generated by `EquipmentCodeGenerator`: category `CAT-0001` and equipment `EQ-000001`.
- Preserve borrow request numbering through `request_sequences`: `BR-YYYYMM-00001`.
- Borrow requests must require accepted borrowing terms and persist both `terms_accepted_at` and `terms_version`.
- Record significant mutations through `App\Support\Auditing\AuditLogger` with useful old/new values and stable event names.

## Authorization and Security

- Enforce authorization server-side with route permission middleware, Policies/Gates, and Spatie Permission as appropriate. Hiding a button is not authorization.
- Scope queries to the current user unless the user has the permission to view all records. Prevent IDOR on every model-bound action.
- Pass only validated, explicitly selected attributes into Actions. Never use `$request->all()` for persistence.
- Keep model `$fillable` lists narrow and intentional.
- Use Blade escaped output (`{{ }}`) for user-controlled data. Do not render raw HTML unless the value is trusted and the reason is documented.
- Preserve CSRF protection for state-changing web requests.
- Use Eloquent/query bindings; never concatenate untrusted values into SQL.
- Validate uploaded file type, MIME, size, extension, and storage path before adding any file-upload feature. Store uploads outside executable public paths unless public access is explicitly required.
- Do not inspect, print, commit, or expose `.env`, tokens, passwords, session data, OIDC claims, or other secrets. `.env.example` is safe to inspect.
- Authentication uses Authentik/OIDC. Do not add a local password login path unless the user explicitly requests and approves the security design.

## Database Rules

- Add a new migration for schema changes; do not rewrite migrations that may already be applied.
- Define foreign keys with an intentional delete behavior, plus appropriate unique constraints and indexes.
- Keep migrations compatible with PostgreSQL and the SQLite test environment where practical.
- Avoid database-specific raw SQL unless there is a documented need and a tested fallback.
- Preserve soft-deleted values when checking identifiers protected by database-wide unique constraints.
- Do not run `migrate:fresh`, destructive SQL, mass deletion, or production seeders without explicit user authorization.
- Seeders must be idempotent. Workflow/demo seeders should cover every Enum state without duplicating data on repeated runs.

## Eloquent and Performance

- Prevent N+1 queries with `with()`, `withCount()`, constrained relationships, or aggregate queries.
- Select only the columns required when loading large or nested relationships.
- Paginate list and report pages; retain validated filters with `withQueryString()`.
- Validate filters before building queries.
- Prefer grouped aggregate queries over repeated count queries when readability remains good.
- Use cache, queues, and Redis only for work that benefits from them. Define invalidation, retry, and failure behavior when introducing them.
- Do not cache permission-sensitive data without including the user/scope in the key and defining invalidation.

## Frontend Rules

- Reuse `resources/views/layouts` and the existing Bootstrap-based visual language.
- Keep visible UI copy in natural Thai and ensure empty, loading, validation, and unauthorized states are clear.
- Keep pages responsive and compatible with the existing dark theme.
- Use local frontend assets under `public/template`; do not introduce CDN dependencies.
- Use the bundled Bootstrap, Lucide, and ApexCharts versions before adding another UI/chart dependency.
- Use semantic labels, keyboard-accessible controls, useful ARIA attributes, and accessible modal behavior.
- Server validation is mandatory even when JavaScript also disables or validates a control.
- Encode PHP data passed to JavaScript with Blade JSON helpers such as `@json` or `@js`; never build executable JavaScript from unescaped user strings.

## Testing Expectations

- Add or update tests for meaningful business rules, validation, authorization, query scoping, workflow transitions, and persisted side effects.
- Use Feature tests for HTTP behavior and integration boundaries. Use Unit tests for isolated Enum or domain behavior.
- Assert both the successful path and important failure/authorization paths.
- Verify database state, related state changes, and audit events for workflow mutations.
- Keep tests deterministic. Do not rely on external Authentik, network services, Redis, queues, or the developer database.
- Tests run with in-memory SQLite, array cache/session, and synchronous queues as configured in `phpunit.xml`.
- For view/query changes, consider enabling `Model::preventLazyLoading()` in the relevant regression test.
- Do not delete or weaken existing assertions merely to make a change pass.

## Working Method

1. Read the relevant routes, Controller, FormRequest, Action/Service, Model, migration, view, and tests before editing.
2. Search with `rg`/`rg --files` and follow existing naming and namespace patterns.
3. Preserve unrelated user changes and avoid broad formatting or refactors outside the requested scope.
4. Implement the complete vertical slice, including validation, authorization, persistence, UI states, audit behavior, and tests where applicable.
5. Review security, query count/N+1 risk, transaction boundaries, database constraints, and mass assignment before finishing.
6. Run Pint and relevant tests. Apply new migrations only when the task authorizes implementation and the target database is clearly the local project database.
7. Report changed behavior, migrations, test results, and any verification limitation concisely in Thai.

Make reasonable assumptions for reversible, in-scope implementation details. Ask the user only when a missing choice would materially change business behavior, security, data ownership, or an irreversible action.

## Code Review Rules

- Prioritize authorization bypasses, IDOR, broken workflow transitions, lost auditability, race conditions, data loss, secret exposure, unsafe uploads, and N+1/query regressions.
- Treat missing server-side validation or relying only on disabled/hidden UI controls as a defect.
- Treat multi-record mutations outside a transaction as a defect unless atomicity is demonstrably unnecessary.
- Treat status strings that bypass existing Enums as a defect.
- Treat new CDN assets or production dependencies without a clear project need as a defect.
- When reporting a problem, identify the concrete failure mode and recommend the smallest safe fix.
